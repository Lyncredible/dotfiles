# Antigen startup races and the dotfiles fix

Updated: 2026-11-11. Upstream behavior described here is Antigen v2.3.0.

Opening several terminals or tmux panes starts several independent Zsh processes.
They share Antigen's plugin directories and startup caches. Antigen's own lock
ends before cache generation finishes, so those processes can interfere with one
another. Its v2.3.0 cache changes reduce the risk but do not provide mutual
exclusion.

Our fix puts an OS-managed lock around the complete synchronous Antigen setup and
periodic update sequence. It replaces our earlier directory/PID lock, whose
recovery logic had races of its own. This document explains both layers, how the
new implementation works, and where its guarantees end.

## 1. What happens when a shell starts

The startup path in this repository is:

```text
~/.zshrc                         wrapper created by setup.sh
  source ~/.zshrc_pre            optional local overrides
  source ~/.dotfiles/.zshrc
    source common.sh             helper functions, including our lock
    maybe_update_dotfiles        periodic dotfiles fetch/rebase
    source main.zshrc
      configure_antigen          configure/load plugins and possibly update them
  source ~/.zshrc_post           optional local customizations
```

`source` executes a file inside the current shell. Plugin loading must happen
there so that its functions, aliases, environment variables, and hooks remain
available at the prompt. Running initialization in a separate process and waiting
for it would lose those changes.

Antigen records the requested plugins through commands such as `antigen use`,
`antigen bundle`, and `antigen theme`. During startup it can defer work until
`antigen apply`. With caching enabled, it generates a script that restores
configuration and sources the selected plugins. Later shells can load that script
instead of rebuilding the setup.

The important shared files are, by default:

| File under `~/.antigen/` | Purpose |
| --- | --- |
| `init.zsh` | Generated startup script, including configuration and plugin source statements. |
| `init.zsh.zwc` | Compiled form of that script, generated by Zsh's `zcompile`. |
| `init.zsh.tmp`, `init.zsh.tmp.zwc` | Temporary files used by Antigen v2.3 during generation. |
| `.resources`, `.zcompdump` | Configuration-dependency metadata and completion-cache data. |
| `.lock` | Antigen's own presence-based lock file. |
| `.dotfiles-cache.lock` | Our persistent file used for an OS-managed lock. |

`ADOTDIR` can relocate Antigen's shared state; `ANTIGEN_CACHE` can change the main
cache path. A `.zwc` file contains parsed shell code, not a standalone executable.
Zsh can use a suitable compiled file when sourcing the corresponding script.

The original symptoms included missing plugins, lost `ls` colorization, an empty
`ZSH` value in the generated cache, and Antigen's message about another process
running. Here, `ZSH` is an oh-my-zsh configuration variable containing its install
path. These symptoms are clues, not conclusive tests: an empty variable alone
does not identify which startup operation failed.

## 2. The upstream root cause: the lock ends too early

Antigen implements extensions using hooks: callbacks attached before, after, or
in place of another function. The public `antigen apply` command dispatches to
`antigen-apply`, whose execution includes these hooks.

The relevant post hooks run in this order:

```text
antigen-apply-lock       remove Antigen's .lock file
antigen-apply-cached     generate and load the startup cache
```

Other hooks participate in initialization, but these two establish the bug:
**Antigen releases its lock while the operation still has shared writes to do.**
The lock-release callback is a post hook on an internal function, not a guarantee
that everything behind the public `antigen apply` call has finished.

Before v2.3, cache generation wrote directly to `init.zsh` and launched compilation
in the background. One possible execution was:

```text
Step  Shell A                             Shell B
----  ----------------------------------  ---------------------------------
1     finishes the core apply operation
2     post hook removes .lock
3                                         enters Antigen initialization
4     cache hook starts writing init.zsh
5                                         reaches its own cache generation
6     writes/compiles the shared cache     writes/compiles the same cache
```

There is no exclusion between steps 4 and 6. Opening a file with `>` truncates it;
concurrent writes need not produce one complete writer's output. A reader can
also source a file while another shell is still writing it. Because the cache
contains executable shell code and captured configuration, failures can appear
as missing setup rather than an obvious file-format error.

Antigen's acquisition also has a separate weakness: it checks whether `.lock`
exists and then calls `touch`. Those are separate operations. Two shells can both
observe an absent file and both proceed. Changing hook order alone would not fix
that acquisition race.

The relevant upstream code is in
[`src/ext/lock.zsh`](https://github.com/zsh-users/antigen/blob/v2.3.0/src/ext/lock.zsh),
[`src/ext/cache.zsh`](https://github.com/zsh-users/antigen/blob/v2.3.0/src/ext/cache.zsh),
and the hook dispatcher in
[`src/ext/ext.zsh`](https://github.com/zsh-users/antigen/blob/v2.3.0/src/ext/ext.zsh).

## 3. What upstream v2.3 fixed, and what it did not

[PR #755](https://github.com/zsh-users/antigen/pull/755), merged July 14, 2026 and
included in v2.3.0, changed the main cache-generation sequence to:

```text
write init.zsh.tmp
compile init.zsh.tmp synchronously into init.zsh.tmp.zwc
rename init.zsh.tmp to init.zsh
rename init.zsh.tmp.zwc to init.zsh.zwc, if present
```

Synchronous compilation means the shell waits for that `zcompile` call to return.
Renaming a completed temporary file into place avoids exposing that writer's
partially generated file at the final pathname. These are useful improvements.

However, every shell uses the same temporary pathname. For example:

1. A writes `init.zsh.tmp` and is about to compile it.
2. B opens that same pathname and overwrites its contents.
3. B compiles and renames the temporary files into place.
4. A resumes and tries to compile or rename a temporary file that has disappeared.

We reproduced missing-temporary-file errors with v2.3.0. Concurrent startup also
produced incomplete plugin loading. The early unlock still exists, and the two
final renames do not publish the source/compiled pair as one atomic operation.

A rename makes one pathname change atomic. It does not serialize writers, make a
shared temporary filename safe, or make a multi-file update atomic. That is why
we retain an outer lock.

## 4. Why our first outer lock was insufficient

Our earlier wrapper acquired a directory with `mkdir`, wrote the holder's PID
inside it, and released it with `rm -rf`. It correctly extended the lock boundary
past `antigen apply`, but its recovery and cleanup logic introduced other paths
to overlapping work or failed startup.

| Failure | What went wrong |
| --- | --- |
| Timestamp race | A disappearing directory and mixed `stat` output broke age calculation. |
| Live-holder eviction | Age above five minutes could override a live PID. |
| Unowned release | An old holder could delete a replacement holder's directory. |
| Signal handling | A caught INT/TERM could release the lock while initialization continued. |
| Incomplete scope | Periodic Antigen updates ran after release, while modifying shared state. |

In the timestamp case, the directory could disappear after an existence check.
The GNU `stat` call then failed; a BSD-syntax fallback on GNU `stat` could emit
filesystem information if another shell had recreated the directory. That output
was not a numeric timestamp, and the subsequent arithmetic aborted startup.
The signal handlers also replaced any handlers the caller had already installed.

`mkdir` itself provided atomic acquisition. The fragile part was deciding when
another process's directory was safe to delete, then deleting it while ownership
could change. During investigation, 3 of 24 wrapped shell starts aborted in the
timestamp calculation. That demonstrates a real failure; it is not an estimate
of the failure rate in everyday use.

## 5. The new fix, step by step

The implementation is in [common.sh](common.sh) and
[`configure_antigen()` in main.zshrc](main.zshrc).

### Step 1: Use one persistent file for the shared state

The default lock pathname is:

```zsh
${ADOTDIR:-$HOME/.antigen}/.dotfiles-cache.lock
```

`${variable:-default}` means “use the variable when nonempty, otherwise use the
default.” `ANTIGEN_DOTFILES_LOCK` can override the complete lock pathname. Every
shell accessing the same Antigen state must use the same lock file.

The file's existence does not mean it is locked. It remains on disk between
sessions; ownership is tracked by the OS. We never unlink it during release or
recovery. Otherwise, one shell could still hold a lock on the old inode while
another creates and locks a new file at the same pathname.

The old `.dotfiles/.antigen-cache.lock/` directory is no longer used and is not
automatically removed.

### Step 2: Acquire the lock in the initializing shell

`acquire_antigen_cache_lock()` loads Zsh's native system module, checks that file
locking is supported, validates the timeout, and ensures the lock file exists.
It then calls:

```zsh
zsystem flock -t "$ANTIGEN_LOCK_TIMEOUT" -i 0.05 -f lock_fd "$lock_file"
```

This is a Zsh builtin, not a dependency on an external `flock` command. It uses
OS-level `fcntl` advisory locking. `-t` sets the maximum wait, `-i` sets the retry
interval in seconds, and `-f` stores the acquired file descriptor in `lock_fd`.
The default timeout is 30 seconds.

Acquisition is exclusive: a cooperating second shell waits or times out. An
unsupported module, invalid timeout, file error, or acquisition failure returns
an error. `configure_antigen()` then reports the problem and skips Antigen setup;
it does not fall through into unlocked initialization.

The builtin runs in the same shell that loads the plugins. There is no separate
initialization process whose environment changes would be lost.

### Step 3: Keep ownership through setup and updates

The protected sequence is:

```text
acquire outer lock
  source antigen.zsh
  configure oh-my-zsh, bundles, and theme
  antigen apply
  perform the legacy compilation check, if applicable
  antigen selfupdate and antigen update, when the periodic update is due
release outer lock
```

Acquisition happens before sourcing Antigen because sourcing can inspect caches
and invalidate them when configuration changes. Locking only around `apply`
would leave those earlier operations exposed.

Updates now share this boundary because `selfupdate` can reset cache files and
`update` modifies plugin checkouts. A warm-cache startup also takes the lock, so
its managed cache reads do not overlap another managed initialization or update.

The synchronous Antigen setup calls use `|| return` to stop on reported failure.
In shell syntax, that means “if the command failed, return from this function.”
Cleanup still runs on that return.

### Step 4: Release through scoped cleanup, without replacing signal handlers

The structure is a Zsh-specific equivalent of `try`/`finally`:

```zsh
{
  # Protected initialization and optional updates.
} always {
  release_antigen_cache_lock
}
```

The `always` block provides cleanup when control leaves the protected block,
including an early return. We no longer install handlers that unlock immediately
on INT or TERM, and we leave the caller's existing handlers intact.

This distinction matters when a signal is caught: if a handler returns and work
continues, the lock must remain held. A deterministic test pauses `antigen apply`,
sends TERM to a shell with an existing TERM handler, and verifies that a second
shell still cannot acquire the lock until initialization resumes and finishes.

If the owning shell exits, the OS releases its lock. SIGKILL cannot run shell
cleanup, but it still releases the OS-managed ownership when the process dies.

### Step 5: Guard against accidental ownership mistakes

The helper records the descriptor and owning process in unexported shell
variables. Release closes the descriptor only when the current process matches
the recorded owner, then clears those variables. Calling release without
ownership is harmless.

Zsh has a subtlety here: `$$` retains the main shell's PID inside a subshell.
`${sysparams[pid]}`, provided by `zsh/system`, identifies the actual current
process. We use that value so inherited variables are not mistaken for ownership
in a subshell.

Nested acquisition is rejected before opening the file again. Traditional
`fcntl` locks have another subtlety: closing another descriptor for the same file
in the owning process can release its locks. The rejection preserves the outer
operation's ownership instead of trying to make these helpers reentrant.

See the [Zsh system-module documentation][zsh-system] for the locking API and
its descriptor semantics.

[zsh-system]: https://zsh.sourceforge.io/Doc/Release/Zsh-Modules.html#The-zsh_002fsystem-Module

### Step 6: Avoid timestamp polling when compilation is already synchronous

The old `wait_for_antigen_compile()` looked for a `.zwc` file strictly newer than
the source. That cannot prove a background writer has finished: its output file
may exist and have a new timestamp while it is still open. Equal timestamps can
also make a completed compile appear unfinished.

The helper now checks the generated cache's `_ANTIGEN_CACHE_VERSION`. For v2.3.0
and newer it returns immediately, since main-cache compilation already completes
inside `antigen apply`. For older or unknown versions, the existing polling is
retained as best-effort compatibility, with a default limit of five seconds.

This also fixes a startup-latency problem. In a test with real v2.3.0, unnecessary
five-second waits accumulated behind the exclusive lock and caused queued shells
to time out. With the version check, all three batches of eight shells completed
in roughly 1.1 seconds per batch without warnings.

## 6. What the tests establish

Run the complete checks with:

```sh
make check
```

To run only the independent-process locking tests:

```sh
make test-integration FILES=spec/integration_antigen_lock.sh
```

The tests cover different properties rather than relying only on a stress loop:

| Coverage | Evidence |
| --- | --- |
| Contention and handoff | A probe fails while the holder is paused; a waiter succeeds on release. |
| Ownership | Nested, subshell, and unowned releases cannot free a live holder's lock. |
| Old timestamps | Making the lock file old does not permit takeover. |
| Outer-lock crash recovery | A fresh process acquires after the holder dies from TERM or KILL. |
| Concurrent cache work | Three batches of eight processes generate, compile, and read fixtures. |
| Configuration boundaries | Separate-process probes cover setup and periodic updates. |
| Failure cleanup | Source/command failures release ownership; caller traps survive. |
| Caught signals | TERM during paused initialization does not unlock early. |
| Compatibility/errors | Unsupported locking, invalid inputs, and compilation version checks. |

The cache-writer test uses an independent directory assertion to detect overlapping
protected sections. The handoff and signal tests use explicit readiness markers
to establish the relevant ordering, rather than hoping a particular scheduling
race happens during a loop.

At the time of this change, `make check` passed 155 unit examples and both
integration suites on Linux. A separate investigation test used the installed
Antigen v2.3.0 with fixture plugins in temporary homes: all 24 shell starts loaded
the expected fixtures without warnings. That real-Antigen test is additional
evidence, not part of the checked-in, stub-driven suite.

These tests avoid deleting or rebuilding the user's actual Antigen cache.
macOS runtime testing remains outstanding.

## 7. Boundaries and remaining risks

The guarantee is that cooperating dotfiles startup operations do not overlap
inside the protected synchronous section. It is not a transaction over every
file Antigen can touch.

- **Manual commands:** Direct `antigen` commands outside this wrapper do not take
  our outer lock. Antigen's internal lock remains enabled, with its upstream
  limitations. Separate lock-path overrides can also defeat cooperation.
- **Background workers:** A child does not inherit its parent's `fcntl` lock
  ownership. Pre-v2.3 main-cache compilation, and v2.3 background work on
  completion/configuration caches, are not joined by this wrapper. Such work can
  outlive the protected section or the owning shell.
- **Interrupted upstream state:** OS recovery frees our outer lock; it does not
  repair an interrupted cache write or remove Antigen's own leftover `.lock`.
  The crash-recovery tests establish outer-lock availability, not complete
  recovery of all Antigen state.
- **Dotfiles updates:** `maybe_update_dotfiles()` runs before this lock is acquired.
  Its fetch/rebase operations are a separate coordination problem.
- **Slow updates:** Keeping network updates inside the lock can delay other
  starting shells. Waiters have a bounded timeout and report failure rather than
  taking over an active lock. Moving maintenance out of startup is separate work.

The fix removes our unsafe stale-lock recovery and protects the main cache path
through synchronous generation, loading, and managed updates. Broader maintenance
coordination and upstream background-worker behavior remain explicit follow-up
work.
